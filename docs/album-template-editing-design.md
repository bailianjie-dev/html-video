# 电子相册模板机制与可控编辑方案设计

## 1. 背景

当前电子相册第一版已经实现了基础能力：用户输入主题或提示词后，系统调用大模型生成一个可预览的电子相册页面。这个版本验证了“AI 根据用户需求生成相册”的核心链路，但还偏向一次性生成，产品可控性不足。

领导提出的 PPT 生成项目中包含两个关键能力：

1. 用户生成前可以选择模板。
2. 生成后用户可以修改部分内容或样式，并且部分修改不需要再次调用大模型。

这两个能力对应电子相册产品的下一阶段方向：从“让 AI 生成一个结果”升级为“基于模板生成，并支持可控编辑”。

## 2. 当前第一版现状

当前版本的主流程可以概括为：

1. 用户输入相册主题、场景、页数、比例等生成要求。
2. 用户可选择模板。
3. 系统创建项目并保存用户选择。
4. 后端读取模板信息，将用户输入、模板信息、素材信息组织成 prompt。
5. 大模型根据 prompt 生成电子相册 HTML。
6. 系统保存生成结果，用户进入项目页预览。
7. 用户后续调整主要仍依赖再次向大模型发送修改要求。

当前已经具备模板目录 `templates/`，模板里通常包含：

- `template.html-video.yaml`：模板元数据，声明模板 id、名称、描述、入口文件、支持比例等。
- `source/index.html` 或其它 `source_entry` 指向的入口 HTML：用于给大模型提供视觉参考。
- `preview.png`、`poster.svg`：用于模板库卡片或预览。
- `SKILL.md`、`example.md`：用于描述模板风格、示例输入和使用约束。
- `assets/`：模板运行或预览所需的图片、字体、素材等。

目前模板的核心作用是“视觉参考”：用户选择模板后，程序读取模板 metadata 和入口 HTML，将其作为上下文传给大模型，让大模型参考模板的版式、配色、字体和动效来生成新的相册。

## 3. 当前问题

第一版功能可以演示，但还存在几个产品化问题：

1. 模板约束偏弱

   当前模板主要通过 prompt 传递给大模型。大模型会参考模板，但最终结果仍存在不稳定性，可能出现风格偏移、结构变化、部分细节没有遵守模板等问题。

2. 生成结果不够结构化

   如果最终结果只是一整段 HTML，程序很难准确知道哪些是标题、正文、图片、按钮、背景色、品牌色。后续编辑时只能让大模型重新改，或者直接操作 HTML 字符串，维护成本高。

3. 用户修改过度依赖大模型

   用户只是想改标题、换图片、调整背景色时，如果再次调用大模型，可能带来两个问题：

   - 结果不可控：大模型可能顺手改了其它内容或结构。
   - 成本和耗时增加：简单修改不应该每次都重新生成。

4. 产品流程还不够明确

   目前已经有生成能力，但还需要明确模板库、模板选择、生成后编辑、导出之间的完整产品闭环。

## 4. 目标

下一阶段建议围绕三个目标建设：

1. 模板可视化

   用户可以在生成前进入“风格模板”菜单，浏览模板缩略图和大预览，并选择模板用于创建相册。

2. 基于模板生成

   用户选择模板后，系统不仅把模板名称传给大模型，还应该把模板的元数据、入口 HTML、风格说明等组织成明确的生成上下文，让大模型按模板生成。

3. 生成后可控编辑

   对于标题、正文、图片、颜色、按钮文案、联系方式等简单修改，程序应该直接修改结构化变量或配置，而不是再次请求大模型。

## 5. 推荐产品流程

### 5.1 创建相册流程

推荐流程：

1. 用户点击“新建相册”。
2. 用户填写主题或粘贴资料。
3. 用户选择页数、场景、比例。
4. 用户选择模板，支持模板可视化预览。
5. 用户点击“生成相册”。
6. 系统创建项目，保存用户输入、模板 id、比例、页数等配置。
7. 系统调用大模型生成相册。
8. 用户进入项目页预览和编辑。

模板选择建议作为生成前的核心配置项，但不强制用户必须选择。如果用户不选，系统使用默认模板或根据场景自动匹配模板。

### 5.2 风格模板菜单流程

新增左侧菜单“风格模板”，第一版可以包括：

1. 模板列表：展示模板名称、描述、缩略图、标签。
2. 模板预览：点击模板后打开大尺寸预览。
3. 用此模板创建相册：选择模板后回到创建页，并自动带入该模板。
4. 应用到当前项目：如果用户当前已经打开某个项目，可以把模板保存到该项目，后续重新生成时按该模板执行。

第一版不建议直接支持用户上传模板代码，因为模板代码涉及安全、校验、兼容性和预览稳定性。可以后续分阶段支持。

### 5.3 生成后编辑流程

生成后建议把编辑分成两类：

1. 程序可控编辑

   不调用大模型，直接修改结构化字段或变量。

   适合：

   - 修改标题
   - 修改正文
   - 替换图片
   - 修改品牌色
   - 修改背景色
   - 修改按钮文案
   - 修改联系方式
   - 修改 Logo

2. AI 辅助编辑

   需要重新调用大模型。

   适合：

   - 重新规划整本相册结构
   - 增加新页面
   - 改变整体表达风格
   - 根据新资料重写文案
   - 大范围换风格

产品上应该优先提供程序可控编辑，让用户觉得结果稳定、可控；只有复杂调整才进入 AI 再生成流程。

## 6. 模板信息如何传给大模型

用户选择模板后，系统应该将模板信息分层传给大模型。

### 6.1 模板元数据

来自 `template.html-video.yaml`，包括：

- 模板 id
- 模板名称
- 模板描述
- 支持比例
- 默认时长
- 标签
- 模板入口文件

作用：告诉大模型当前模板是什么，适合什么内容，输出需要满足什么约束。

### 6.2 模板入口 HTML

来自 `source_entry` 指向的文件，常见是：

```text
templates/<template-id>/source/index.html
```

作用：作为视觉参考，让大模型理解模板的：

- 页面结构
- 布局方式
- 字体风格
- 色彩体系
- 动效方式
- 页面切换方式
- 组件样式

当前实现里，后端会读取该 HTML，并截取部分内容放进 prompt。

### 6.3 模板风格说明

可以来自 `SKILL.md` 或未来新增的结构化字段，例如：

```yaml
style_guide:
  tone: "科技、简洁、克制"
  layout: "大标题 + 数据卡片 + 分屏图文"
  motion: "轻量淡入和纵向滚动"
  avoid:
    - "不要使用复杂 3D"
    - "不要堆叠长段落"
```

作用：用自然语言或结构化配置明确告诉大模型该模板的设计规则。

### 6.4 用户输入和素材信息

包括：

- 用户主题
- 场景
- 页数
- 比例
- 上传素材
- 用户补充说明

大模型最终收到的不是单纯用户 prompt，而是“用户需求 + 模板信息 + 输出约束”的组合。

## 7. 生成结果如何支持可控编辑

要减少对大模型的依赖，生成结果不能只是一整段不可理解的 HTML。建议逐步引入“结构化生成结果”。

### 7.1 在 HTML 中保留可编辑标记

示例：

```html
<h1 data-hv-text="cover.title">大米科技有限公司</h1>
<p data-hv-text="cover.subtitle">专注企业数字化解决方案</p>
<img data-hv-image="cover.logo" src="./assets/logo.png" />
<a data-hv-text="cta.button">联系咨询</a>
```

程序可以通过 `data-hv-text` 找到可编辑文字，通过 `data-hv-image` 找到可替换图片。

用户在右侧编辑面板修改标题时，程序直接找到对应节点并替换文本，不需要重新调用大模型。

### 7.2 使用 CSS 变量控制样式

示例：

```css
:root {
  --primary-color: #2563eb;
  --background-color: #ffffff;
  --title-color: #111827;
  --font-family: "Inter", "Microsoft YaHei", sans-serif;
}
```

用户修改品牌色时，程序只需要替换：

```css
--primary-color: #ff3366;
```

这样可以做到颜色、背景、字体等样式修改可控。

### 7.3 保存一份项目配置 JSON

建议每个项目保存一份结构化配置：

```json
{
  "templateId": "album-scroll-story",
  "aspect": "9:16",
  "theme": {
    "primaryColor": "#2563eb",
    "backgroundColor": "#ffffff",
    "fontFamily": "Microsoft YaHei"
  },
  "pages": [
    {
      "id": "cover",
      "title": "大米科技有限公司",
      "subtitle": "专注企业数字化解决方案",
      "image": "cover.png"
    },
    {
      "id": "business",
      "title": "核心业务",
      "items": ["系统集成", "数据平台", "AI 应用"]
    }
  ]
}
```

后续用户修改时，优先修改这份 JSON，再由程序渲染或同步到 HTML。

### 7.4 推荐的演进方向

短期可以继续保存 HTML，但要求大模型在生成 HTML 时加入 `data-hv-text`、`data-hv-image` 和 CSS 变量。

中期可以让大模型输出：

1. `album.json`：结构化内容和变量。
2. `index.html`：根据结构化内容渲染的页面。

长期可以让模板变成真正的数据驱动模板：

```text
模板 HTML + 模板变量 schema + 用户数据 JSON = 最终相册
```

这样模板和内容分离，产品会更稳定。

## 8. 哪些修改不需要调用大模型

建议程序直接控制：

| 修改类型 | 是否需要大模型 | 实现方式 |
| --- | --- | --- |
| 修改标题 | 不需要 | 替换 `data-hv-text` 对应文本 |
| 修改正文 | 不需要 | 替换 `data-hv-text` 对应文本 |
| 替换图片 | 不需要 | 替换 `data-hv-image` 对应 `src` |
| 修改 Logo | 不需要 | 替换图片变量 |
| 修改品牌色 | 不需要 | 替换 CSS 变量 |
| 修改背景色 | 不需要 | 替换 CSS 变量 |
| 修改按钮文案 | 不需要 | 替换文本变量 |
| 修改联系方式 | 不需要 | 替换文本变量 |
| 新增一页 | 视情况 | 简单模板复制可程序控制，复杂内容建议调用大模型 |
| 重写整本内容 | 需要 | 调用大模型 |
| 换整体风格 | 需要 | 调用大模型或重新套模板 |
| 重新规划结构 | 需要 | 调用大模型 |

## 9. 模板机制建议

建议把模板从“一个 HTML 文件”升级为“模板包”。

每个模板包包含：

```text
templates/<template-id>/
  template.html-video.yaml
  source/
    index.html
  preview.png
  SKILL.md
  example.md
  assets/
```

后续可增强为：

```text
templates/<template-id>/
  template.html-video.yaml
  source/
    index.html
  schema.json
  default-data.json
  style-guide.md
  preview.png
  assets/
```

新增文件说明：

- `schema.json`：声明模板支持哪些可编辑变量，比如标题、图片、颜色、CTA。
- `default-data.json`：模板默认数据，用于预览和初始化。
- `style-guide.md`：给大模型看的风格说明，可以替代或补充 `SKILL.md`。

## 10. 分期计划

### 第一期：模板库与模板选择

目标：让用户知道有模板，并能选择模板生成。

功能：

- 左侧新增“风格模板”菜单。
- 展示模板列表和预览。
- 支持“用此模板创建相册”。
- 支持“应用到当前项目”。
- 生成时保存 `templateId`。
- 生成 prompt 中加入模板 metadata 和入口 HTML。

收益：

- 产品流程更完整。
- 用户能感知模板价值。
- 与领导展示的 PPT 项目形成能力对齐。

### 第二期：生成结果可编辑标记

目标：让生成后的 HTML 支持程序识别和替换内容。

功能：

- 要求大模型生成 `data-hv-text`、`data-hv-image` 等标记。
- 右侧编辑面板读取这些标记。
- 用户修改文字后，程序直接替换 HTML。
- 用户替换图片后，程序直接替换 `src`。

收益：

- 简单修改不再调用大模型。
- 编辑结果稳定。
- 用户体验更像一个真正的编辑器。

### 第三期：样式变量可控

目标：让颜色、字体、背景等样式可以被程序控制。

功能：

- 模板和生成结果统一使用 CSS 变量。
- 提供品牌色、背景色、字体等编辑控件。
- 修改后直接替换 CSS 变量。

收益：

- 风格微调更稳定。
- 降低大模型调用成本。
- 方便做品牌定制。

### 第四期：结构化相册数据

目标：从“编辑 HTML”升级为“编辑相册数据”。

功能：

- 生成时同时产出 `album.json`。
- 页面内容、图片、颜色都保存在 JSON 中。
- HTML 由模板根据 JSON 渲染。

收益：

- 模板和内容分离。
- 后续支持多模板切换更容易。
- 更接近 PPT 项目的变量替换机制。

### 第五期：自定义模板

目标：支持用户或运营方扩展模板。

建议分两步：

1. AI 生成风格预设

   用户描述想要的风格，AI 生成一份安全的样式配置或模板说明，不直接上传可执行代码。

2. 高级用户上传模板包

   支持上传 zip 模板包，但必须经过校验：

   - 是否包含 `template.html-video.yaml`
   - 是否包含入口 HTML
   - 是否符合变量 schema
   - 是否存在危险脚本
   - 是否能正常预览

第一阶段不建议开放用户上传代码模板，风险较高。

## 11. 风险与注意事项

1. 不要把模板只理解成预览图

   模板应该同时服务用户、大模型和程序。用户看预览，大模型看结构和风格，程序看变量和 schema。

2. 不要所有修改都依赖大模型

   大模型适合生成和重构，程序适合替换和控制。产品要把两类能力分开。

3. 不要一开始就做复杂模板上传

   上传模板涉及安全问题和运行兼容性，建议先做内置模板库和 AI 风格预设。

4. 模板 HTML 不能无限制传给大模型

   模板 HTML 可能很长，需要截取关键部分，或者用 `style-guide`、`schema` 做更稳定的摘要。

5. 生成结果必须逐步结构化

   如果始终只保存一整段 HTML，后续可控编辑会越来越难。

## 12. 结论

电子相册项目下一阶段的核心方向不是简单增加几个按钮，而是建立一套“模板 + 生成 + 可控编辑”的产品机制。

建议产品演进路径为：

1. 第一版：用户输入 prompt，AI 生成相册。
2. 第二版：用户选择模板，AI 按模板生成相册。
3. 第三版：生成结果保留可编辑标记，文字和图片可由程序直接修改。
4. 第四版：颜色、背景、字体等样式使用变量控制。
5. 第五版：模板和内容分离，形成真正的数据驱动模板系统。

这样既能保留大模型的生成能力，又能提升产品的稳定性和可控性，避免每次简单修改都重新询问大模型导致结果不可控。
